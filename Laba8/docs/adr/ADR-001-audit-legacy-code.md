# ADR-001: Аудит legacy-коду обробки замовлення та вибір стратегії рефакторингу

## Статус
Прийнято (Accepted)

## Контекст
Вихідний код (варіант 1, «Інтернет-магазин електроніки») складається з п'яти класів:
`Customer`, `Product`, `OrderItem`, `Order` (пасивні контейнери з публічними полями) та
`LegacyOrderProcessor` з єдиним методом `processConsoleOrder()` на 52 непорожні рядки.

Виявлені проблеми:

| # | Проблема | Де саме | GRASP, що порушується |
|---|----------|---------|-----------------------|
| 1 | **Anemic Domain Model**: 19 публічних змінних полів, жодного бізнес-методу | `Customer`(5), `Product`(4), `OrderItem`(2), `Order`(8) | Information Expert, інкапсуляція |
| 2 | **Bloated Controller / Monolithic method**: один метод поєднує 9 обов'язків — ввід з консолі, створення даних, підсумок, знижка, ПДВ, рахунок, збереження, сповіщення, зміна статусу | `processConsoleOrder()` | High Cohesion, Controller |
| 3 | **Feature Envy**: метод звертається до полів чужих класів 47 разів | `order.totalAmount = …`, `item.product.price * item.quantity` | Information Expert |
| 4 | **Порушення Закону Деметри**: 6 навігаційних ланцюжків `order.customer.type`, `item.product.price`, `order.customer.email` | там же | Low Coupling, Law of Demeter |
| 5 | **Procedural branching**: каскад `if / else if` за рядковим типом клієнта (`"VIP"`, `"Regular"`, `"New"`); невідомий тип мовчки дає знижку 0 | розрахунок `discountRate` | Polymorphism, Protected Variations |
| 6 | **Магічні числа**: `0.15`, `0.05`, `0.20`, `15000.0`, `30000.0`, `800.0` | всередині методу | Protected Variations |
| 7 | **Створення об'єктів без контролю**: об'єкт створюється порожнім і заповнюється ззовні (можна отримати `Order` без клієнта чи з від'ємною кількістю) | `new Customer(); customer.id = 1; …` | Creator |
| 8 | **Прив'язка до деталей інфраструктури**: консоль, «БД» і «email» прямо в логіці; збереження лише імітується `println` | кінець методу | Indirection, Pure Fabrication |
| 9 | **Гроші як `double`** і неявні похибки округлення | усі суми | коректність домену |

## Рішення
Рефакторинг у Rich Domain Model із шаруватою архітектурою `ui → application → domain` та
`infrastructure → application`. Обґрунтування конкретних розподілів обов'язків зафіксовано в
окремих документах:

* ADR-002 — Information Expert + Creator (домен);
* ADR-003 — Controller + Indirection + Pure Fabrication (застосунок / CLI);
* ADR-004 — Polymorphism + Protected Variations (знижки, податки, кроки);
* ADR-005 — метрики, компроміси та винятки з цілі CBO ≤ 4;
* QOC-001…QOC-004 — порівняння альтернатив для ключових рішень.

## Наслідки
* **Позитивні:** кожен клас має одну причину для змін; домен не залежить від UI/інфраструктури;
  нові типи клієнтів/податків/каналів додаються без редагування існуючих класів.
* **Негативні / компроміси:** кількість класів зросла з 5 до 38; для простого сценарію це
  «надлишкова» структура, виправдана навчальною метою й очікуваним зростанням системи.
* **Свідомі зміни поведінки:** невідомий тип клієнта тепер відхиляється з помилкою (раніше —
  мовчки без знижки); суми — `BigDecimal` з 2 знаками (раніше `double`, напр. `31600.0`);
  збереження у файл реальне (раніше лише повідомлення); поле `totalSpent` видалено, бо воно
  ніде не читалося (YAGNI).
