# ADR-002: Інкапсуляція бізнес-логіки в сутностях (Information Expert) і контрольоване створення (Creator)

## Статус
Прийнято (Accepted)

## Контекст
У legacy-коді підсумок замовлення, знижка й податок обчислював `LegacyOrderProcessor`, читаючи
публічні поля `Order`, `OrderItem`, `Product`, `Customer` (47 звернень до чужих полів).
Об'єкти створювалися порожніми та заповнювалися покроково ззовні.

## Рішення
**Information Expert** — обчислення живуть там, де лежать дані:

| Обчислення | Власник даних → Експерт |
|------------|-------------------------|
| вартість N одиниць товару | `Product.priceFor(quantity)` |
| сума рядка | `OrderItem.subtotal()` (знає товар і кількість) |
| підсумок, знижка, ПДВ, до сплати | `Order.subtotal() / discountAmount() / taxAmount() / finalAmount()` |
| знижка клієнта | `Customer.discountOn(amount)` |
| перехід `NEW → PROCESSED` з інваріантами | `Order.process()` |

Суми **не зберігаються**, а обчислюються з поточного стану, тому розсинхронізація
`totalAmount` / `finalAmount` неможлива (у legacy вони були окремими полями).

**Інкапсуляція стану:** усі поля `private final` (крім `Order.status`, який змінюється лише
через `process()`); сеттерів немає; колекція рядків захищена `List.copyOf(...)` і при виході
з `Order.items()` лишається незмінною.

**Creator (static factory methods):**
* `Customer.register(...)`, `OrderItem.of(...)`, `Order.place(...)` — приватні конструктори,
  валідація (не порожнє ім'я, email з `@`, кількість > 0, непорожнє замовлення) відбувається до
  створення, тому існує лише валідний об'єкт;
* `Order` не створює `OrderItem` самостійно, щоб не залежати від `Product` (див. ADR-005, CBO(Order)=4).

**Закон Деметри:** замість `order.getCustomer().getName()` — `order.customerName()`,
`order.customerEmail()`, `order.customerType()`; замість `item.getProduct().getName()` —
`item.productName()`.

## Наслідки
* **Позитивні:** публічних змінних полів 19 → 0; звернень до чужих полів 47 → 0; ланцюжків
  Деметри 6 → 0; LCOM4 усіх сутностей = 1.
* **Негативні / компроміси:** `Order` залежить від `OrderItem`, `Customer`, `TaxPolicy`,
  `OrderStatus` (CBO=4, на межі норми); обчислення суми щоразу проходить по рядках (O(n)) —
  для розміру замовлення це незначуще й дешевше за ризик застарілих кешованих значень.
