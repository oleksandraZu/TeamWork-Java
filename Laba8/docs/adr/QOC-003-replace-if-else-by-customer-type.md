# QOC-003: Як позбутися каскаду `if-else` за типом клієнта?

* **Question:** Яким механізмом вибирати поведінку знижки за типом клієнта?
* **Options:**
  * *Option A:* залишити `if / else if`, винести в приватний метод.
  * *Option B:* `enum CustomerType` з абстрактним методом знижки (константи-стратегії).
  * *Option C:* інтерфейс `DiscountPolicy` + класи-реалізації + `DiscountPolicyRegistry`
    (словник «назва → політика»).
* **Criteria:**
  * *Polymorphism:* відсутність умовних операторів за типом.
  * *Protected Variations / OCP:* розширення без зміни існуючого коду (навіть enum).
  * *Простота (KISS):* кількість нових конструкцій.
  * *Обробка невідомого значення:* явна помилка замість мовчазного 0.

| Option | Polymorphism | Розширення без правок | KISS | Невідомий тип |
|--------|:------------:|:---------------------:|:----:|:-------------:|
| A | ✗ | ✗ | ✓ | ✗ (мовчки 0%) |
| B | ✓ | ✗ (правиться enum) | ✓ | ✓ |
| C | ✓ | ✓ (`register(...)`) | ~ (більше файлів) | ✓ (помилка + список) |

* **Conclusion:** обрано **Option C**. Тест `newCustomerTypeCanBeAddedWithoutChangingExistingCode`
  підтверджує розширення без змін. Компроміс: більше класів, ніж у варіанті B, але саме він
  відповідає вимозі лаби про Polymorphism + Protected Variations.
